# Proposed bootstrap executor — not a completed experiment

This proposed runner implements fresh deployment, initial token distribution and sequential consent-gated market packets. No live or fork tests have run. The push-triggered workflow is deliberately disabled pending peer review. Its fixed proposed run ID must never be changed to evade a replay guard; reconcile any prior deployment first. Market handlers are implemented but unreviewed; unattended settlement/shutdown and automatic resume remain unsupported. Existing deployment and old workflow are untouched. `--market` requires the exact bootstrap directory and `APPROVED_ACTION_PACKET` for one sequential virtual day. The simulation should compare the need for guarantees with direct client payment and sponsorship; internal agent behavior and testnet receipts do not establish human earnings.

## Funding and custody

98 run-specific derived wallets represent 40 clients, 40 workers, 14 backers and four sponsors. Issuer and adjudicator are two roles of the existing root wallet. Clients receive 0.8, backers 0.3, sponsors 0.5 and workers zero Circle Base Sepolia test USDC: total 38.2. No reserve funding or staking is automatic. Sponsor reserve choices must spend those sponsor balances; no extra root seed funding is supported. Keys are derived in memory through HMAC over a unique run ID and actor ID, never written or logged. Use repository secret `TEST_WALLET_PRIVATE_KEY` only through the disabled GitHub Actions workflow. No local secret files.

The runner verifies chain 84532, exact root and token, six decimals and a user-supplied reviewed artifact hash. All broadcasts are serialized. A fresh contract is deployed with root owner/issuer/adjudicator and its empty state checked. Receipt validation checks successful status, hash, sender, recipient, chain, nonce, value and calldata; distributions additionally require exact token Transfer logs. It preserves an intent before broadcast, hash immediately afterward, verified receipt logs and balances. It refuses existing evidence directories, root pending transactions and any run-derived character address with a nonzero pending nonce or token balance, before deployment or funding. This prevents a fresh Actions workspace from silently bootstrapping the same run again. An ambiguous send or timeout halts for reconciliation, never retries a send. RPC reads have bounded retries.

## Budget and remaining gates

A conservative gas estimate with 20% gas-limit margin plus twice the live Base GasPriceOracle `getL1FeeUpperBound` for serialized unsigned transaction size plus signature overhead, and a 0.00002 ETH margin is charged against the 0.005 ETH fee cap before sending. Gas funding is separately capped at 0.002 ETH (none currently sent). Token allocations are capped at 40 test USDC. The runner requires Base raw receipt L1 fees and verifies actual combined fees stay within the preflight bound. Live gas-oracle compatibility and fee accounting still require rehearsal. Budget exhaustion leaves a partial bootstrap with its journal, never a completed-market claim. Public RPC outages or state mismatches halt for explicit reconciliation.

Before enabling market execution, independently review strict packets binding `runId`, `intentId`, virtual day (1–7), actor, action, exact payload hash and private consent evidence; independent exact receipts and state imports; agent delivery and client review evidence; deadlines in actual chain time; and the implemented fund-reserve/stake/consent/attest/set-line/open/pay/mark-paid/remit/claim/cancel/pause handlers. Never mark a proposal as opened, simulate deadline expiry from virtual days or invent settlement. Shutdown must reconcile unresolved guarantees, balances, dues and stake rather than force claims. No seven-day or shutdown logs have been produced by this runner. `real-agents-day/1` packets contain runId, day and actions; each `real-agents-action/1` action requires exact actor/action/args plus a consent payload hash and private record hash. Opening additionally requires issuer and client consent record hashes; delivery, client review and verified payment evidence gate settlement actions. Action calldata is retained only as a SHA256 digest to avoid exposing signatures; its exact encoding must be independently reconstructed from privately approved packets.

## Private reviewed consent packet

Market mode also requires `APPROVED_CONSENT_RECORDS` containing `{runId, day, packetSha256, records:[{recordHash,record}]}`. Hashes use SHA256 of compact insertion-ordered JSON. Each actual record has actorId, day, coordinatorApproved=true, actionPayload exactly the normalized action, and transcript with original prompt/response strings and matching actorId/day/acceptedActionPayload. The unmodified response must parse as JSON whose acceptedActionPayload exactly matches. No syntactic hash alone authorizes execution. Worker, client and issuer opening records must carry identical acceptedJob objects binding acceptedJobId, workerId/clientId, wageMicro, guaranteeMicro, termsHash, clientIdHash/groupIdHash, and withholdingAuthorized if the client later remits. New guarantees are capped at 100000 micro-USDC, six per virtual day, and stop after virtual day four. Job records persist only after verified opening and state readback.
